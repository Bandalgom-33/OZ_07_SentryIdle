# 🎮 Unity 3D 팀 프로젝트

## 🤙 커밋 컨벤션 (Commit Convention)

커밋 메시지는 **`Type: Subject`** 형태로 작성합니다.

```text
Feat: 플레이어 이동 로직 추가
```

### Type 종류

| Type | 설명 |
| :--- | :--- |
| `Feat` | 새로운 기능 추가 |
| `Fix` | 버그 수정 |
| `Refactor` | 코드 리팩토링 (기능 변경 없는 구조 개선) |
| `Style` | 코드 포맷팅, 세미콜론 누락, 주석 추가 등 (로직 변경 없음) |
| `Chore` | 빌드 업무, 패키지 매니저 설정, .gitignore 수정 등 |
| `Docs` | 문서 수정 (README 등) |
| `Asset` | 에셋 추가/수정 (이미지, 사운드, 3D 모델, 프리팹 등) |
| `Merge` | 브랜치 병합 |

### 커밋 작성 규칙

- **첫 글자는 대문자**로 시작하며, 문장 끝에 **마침표(.)를 찍지 않습니다**.
- 제목은 **한글**로 명확하고 간결하게 작성합니다.
- 하나의 커밋에는 **최대한 단일 작업 내용만 포함**합니다. (기능 구현과 에셋 추가 분리)

---

## 🌿 브랜치 전략 (Branch Strategy)

본 프로젝트는 **Git Flow 변형 (3계층 구조)**을 사용합니다.

```text
main (최종 제출/배포)
 └── develop (기능 통합/테스트)
      ├── feature/player-controller
      ├── feature/monster-ai
      └── feature/ui-hud
```

| 브랜치 | 역할 |
| :--- | :--- |
| `main` | 최종 빌드 및 제출용 브랜치 (관리자만 병합 가능) |
| `develop` | 작업 결과물 1차 통합 기본 브랜치 |
| `feature/*` | 기능 단위 작업 브랜치 (`feature/기능이름` 형태로 생성) |

---

## 🔀 Pull Request & Code Review 규칙

1. 모든 기능 작업은 `feature/*` 브랜치에서 진행 후 `develop` 브랜치로 **PR을 제출**합니다.
2. PR 제목은 **`[Type] 작업 내용`** 형태로 작성합니다.
   ```text
   [Feat] 플레이어 이동 및 점프 구현
   ```
3. PR 본문에 **주요 변경 사항**과 **테스트 완료 여부**를 간단히 기재합니다.
4. **팀장(소유자) 리뷰 및 승인(Approve)** 후 `develop`에 병합합니다.
5. `develop` → `main` 병합은 **빌드 제출일에만** 팀장이 직접 진행합니다.
